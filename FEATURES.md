# Features

Numbered register of every feature; a number is never reused. Every feature is covered by tests listed in [TESTS.md](TESTS.md); the guard `tests/docs-contract.sh` fails when a feature has no test.

- **F1 — Unprivileged users.** The run user `somebody` and the build user `coder` exist with their home directories; the image switches to `somebody`, so every derived image starts non-root.
- **F2 — Shared group.** The group `shared-access` with the fixed id 500 contains `somebody`, for data shared on volumes between containers.
- **F3 — Variables for derived images.** `RUN_USER`, `RUN_GROUP`, `RUN_HOME`, `BUILD_USER`, `BUILD_GROUP`, `BUILD_HOME`, `SHARED_GROUP_NAME`, `SHARED_GROUP_ID` name the users and groups; `PKG_INSTALL`, `PKG_REMOVE`, `PKG_SEARCH`, `PKG_CLEANUP1`, `PKG_CLEANUP2`, `ALLOW_USER`, `ALLOW_BUILD` are the commands a Dockerfile uses instead of hard coding them.
- **F4 — Language.** `LANG` defaults to `en_US.UTF-8`; a derived image sets another one with the build argument `lang`.
- **F5 — Prompt.** `PS1` is a coloured prompt that shows the container name from `CONTAINERNAME`.
- **F6 — Headless.** The image contains no shell, no busybox and no scripting language, so an attacker who reaches code execution finds no tool to pivot with.
- **F7 — Published for amd64 and arm64.** Every push builds the image natively for both architectures, tests it with `npm test`, deploys it with `npm run deploy` under an architecture tag and joins the architectures under one tag on Docker Hub, only when every step on every architecture succeeded; every image repository of the family uses the same reusable workflow of this repository, which publishes exactly the images its compose file builds.
- **F8 — Tags by date and version.** Every image is published under its tag, the date of the build, and with a version in `package.json` the version with and without the date (`latest`, `20260926`, `1.3.2`, `1.3.2-20260926`; `inotify`, `inotify-20260926`, `inotify-1.3.2`, `inotify-1.3.2-20260926`), so every rebuild stays addressable.
- **F9 — Version branches.** A repository names its version branches with rules that append a suffix to every tag and may put a prefix before the version (`2.x` → `app-2-v2.1.0`; `new-33` → `nginx-33`, …); every push to such a branch builds its version, and the scheduled run of the default branch starts all of them, so every version gets the updates.
- **F11 — The replaced image stays addressable.** Before a build overwrites a tag, the image that carried it gets the tag with the day it was built (`latest` → `20180304`, `app` → `app-20260923`), unless such a tag exists already, so a revert finds the earlier image also where it was published without a date.
- **F10 — Released versions.** A repository names git tags of released versions with `tag` rules; the input `ref` builds such a git tag under its tag and its date (`app-2-v2.0.5`, `app-2-v2.0.5-20261021`), without the version of `package.json`, and the scheduled run starts every such git tag, so a released version gets the security fixes of its base images.
- **F12 — Rebuild when a source changes.** A push, a manual start and a git tag release always build. A scheduled run, which a repository starts every hour, and every run the scheduled run starts on a version branch or for a git tag, builds only when something an image is built from changed since the published image was built, and prints each difference: the digest of a parent image named in `FROM` or `COPY --from` (with the defaults of a global `ARG` and the build arguments of the compose file; stages, `scratch` and images of the same compose file are no parents); a download named literally in `ADD` or in a `RUN` with `wget` or `curl`, an address below `/releases/latest` by the release its redirect names, any other by `ETag` or `Last-Modified`; an image older than `rebuild-days` (default 7), which covers the installed packages and the addresses assembled in shell code; and an image that is not published or carries no record of its sources. A parent image that cannot be looked up fails the run with the error of the registry. Every build records its parents and downloads as labels of the image it publishes, also where the tests build the image once more through a compose file of their own; a pushed image without them fails the run, and the next check reads them from the published image and names the labels it finds there.
- **F13 — Keep-alive.** Every scheduled run enables the repository's own workflow `docker.yml` through the GitHub API, so the run does what GitHub's documented manual re-enabling does; whether that keeps GitHub from disabling scheduled workflows after 60 days without activity, GitHub does not document. A repository whose workflow token lacks the right to manage workflows gets a warning, and its run continues.
